# Native ↔ PWA parity audit

**Date:** 2026-09-08 · **Scope:** `apps/native` vs `apps/pwa` against `apps/server` at commit `210204c`.

**Method.** Three domain sweeps (identity/recovery, economy/marketplace, social/pulse/shell) were run by
Antigravity agents; the full reports are kept verbatim in [`docs/parity/`](parity/). The endpoint coverage
matrix in [`docs/parity/endpoint-matrix.md`](parity/endpoint-matrix.md) was generated by script. Every finding
in the "Verified findings" section below was then re-checked by hand against the code. The eight looser leads
from the first pass were put through a second verification run, whose verdicts are summarised further down —
one of them was refuted outright.

## Headline

The parity gap has reversed direction and the README has not caught up. Native is now the lead client:
134 source files and 361 commits touching `apps/native` in the last 90 days, against 48 files and 121 commits
for `apps/pwa`. [README.md:433](../README.md) still claims the PWA is "fully functional" with the native app at
"near-complete parity" — that sentence describes 2026, not now, and it is the first thing to fix because it
sets the wrong expectation for anyone choosing which client to point a community at.

The PWA is not a thin client of the same product any more. It is missing Pulse entirely, has no working
push, no blocklist, no minimum-version gate, and cannot participate in the recovery system that native
enrols members into.

## Verified findings

Each of these was confirmed by reading the cited code during this audit.

### 1. A PWA-created identity cannot enrol keepers after pairing to a phone — HIGH
`enrolSsoKeeper` and `enrolFriendKeepers` do `hexToBytes(identity.privateKey)` and refuse anything that is not
32 bytes ([keeper-enrolment.ts:218](../apps/native/utils/keeper-enrolment.ts), and again at
[:370](../apps/native/utils/keeper-enrolment.ts)). The PWA stores the key as a 48-byte PKCS8 envelope, and QR
pairing carries it across verbatim, so enrolment fails with `private key is 48 bytes, expected 32` — an error
the member can do nothing about. The code comment above the guard asserts "The identity's privateKey IS the
32-byte Ed25519 seed", which is true only for phone-created identities.

`toEd25519Seed()` ([ed25519-key.ts:70](../packages/beanpool-core/src/ed25519-key.ts)) exists precisely to
normalise both formats, and `native/utils/crypto.ts`, both `e2e-crypto.ts` files and core's `keeper-crypto.ts`
already use it. `keeper-enrolment.ts` is the consumer that was missed. **Fix: one call per guard.**

### 2. A PWA member chosen as a keeper is a black hole — HIGH
Native lets a member designate any active member as a keeper, and approves incoming requests through
`POST /api/recovery/approve-keeper` ([IncomingRecoveryApprovalModal.tsx](../apps/native/components/IncomingRecoveryApprovalModal.tsx)).
The PWA's recovery surface is the legacy guardian flow only — `lookup`, `request`, `pending`, `approve`,
`reject`, `cancel`, `status` ([api.ts:1062-1090](../apps/pwa/src/lib/api.ts)) — with no `approve-keeper` call
anywhere. A keeper on the web cannot release a fragment, so enough web keepers makes the threshold
unreachable and the recovery unfinishable.

### 3. Native project voting posts to a route that does not exist — HIGH
[db.ts:1849](../apps/native/utils/db.ts) posts to `/api/crowdfund/projects/vote`. The server's only vote handler
is `POST /api/commons/vote` ([commons.ts:79](../apps/server/src/routes/commons.ts)); the crowdfund family has
no `vote` member, and the one route that pattern-matches (`/api/crowdfund/projects/:id`) is GET-only. The PWA
calls the correct route ([api.ts:944](../apps/pwa/src/lib/api.ts)). So voting works on web and 404s on the phone.

### 4. Both clients understate partners-to-next-tier by 10× — HIGH
`PER_COUNTERPARTY_VOLUME_CAP = 500` is the canonical knob
([trust.ts:21](../packages/beanpool-engine/src/trust.ts), commented "single source of truth ... do not
duplicate"). Both clients duplicate it anyway as `PER_COUNTERPARTY_CAP = 5000` —
[native ledger.tsx:33](../apps/native/app/(tabs)/ledger.tsx) and
[PWA LedgerPage.tsx:44](../apps/pwa/src/pages/LedgerPage.tsx) — and divide by it to show progress. Every member
is told they need a tenth of the trading partners they actually need. Identical in both clients, so it is a
copy bug rather than a parity bug, but it surfaced here.

### 5. Both clients state the wrong send gate
The server blocks a send when `earnedCredit <= 0` — i.e. until a first completed trade
([state-engine.ts:1213](../apps/server/src/state-engine.ts)) — and the route says so
([community.ts:1054](../apps/server/src/routes/community.ts)). Both clients gate the button on
`balance > 0` and tell the member "Anyone with a positive balance can send"
([native ledger.tsx:406](../apps/native/app/(tabs)/ledger.tsx),
[PWA LedgerPage.tsx:161](../apps/pwa/src/pages/LedgerPage.tsx)). A member who was gifted or granted beans but
has never traded sees an unlocked send button and a server rejection. Note this contradicts the older
"send gate = positive balance" rule of thumb; the server now enforces trade activation.

### 6. PWA notification toggles deliver nothing — HIGH
[SettingsPage.tsx:167](../apps/pwa/src/pages/SettingsPage.tsx) saves chat/marketplace/escrow notification
preferences. The PWA has no `Notification.requestPermission`, no `PushManager`, no push-token registration,
and `selfDestroying: true` on the Vite PWA plugin ([vite.config.ts](../apps/pwa/vite.config.ts)) means there is
no service worker to receive a push. Native registers tokens in
[push-notifications.ts](../apps/native/services/push-notifications.ts). The toggles are a promise the web
client cannot keep.

### 7. PWA members cannot block anyone — HIGH
`bp_blocked_users` is read once, in [MarketplacePage.tsx:1910](../apps/pwa/src/pages/MarketplacePage.tsx), and
is **never written anywhere in the PWA** — no block action exists on the profile or message screens. Native
implements the full block/report path ([blocklist.ts:74](../apps/native/utils/blocklist.ts)). A member being
harassed has a remedy on the phone and none on the web.

### 8. The PWA ignores `minAppVersion`
`minAppVersion` appears **zero times** in `apps/pwa/src`. Native reads it from health and blocks
([GlobalHeader.tsx:267](../apps/native/components/GlobalHeader.tsx)). When an operator raises the floor to force
a protocol update, web clients carry on regardless.

### 9. Pulse is absent from the PWA
The PWA tab union is `'map' | 'marketplace' | 'messages' | 'people' | 'ledger' | 'projects'`
([App.tsx:75](../apps/pwa/src/App.tsx)) — no Pulse tab, against native's feed, channel management, manual
intake and OAuth linking. The only PWA pulse artifact is read-only channel chips on profiles
([ChannelChips.tsx](../apps/pwa/src/components/ChannelChips.tsx)).

### 10. Dead code in the PWA
- `PrivacyBadge` and the 4-tier privacy logic it wraps are built and never mounted — the only other mention is
  a stale comment at [App.tsx:7](../apps/pwa/src/App.tsx). Settings implements an unrelated binary toggle instead.
- `getNodeStats()` calls `GET /api/stats`, which **no server route defines**; the helper swallows the 404
  (`catch { return null }`) and Settings renders nothing ([api.ts:1107](../apps/pwa/src/lib/api.ts), called from
  [SettingsPage.tsx:220](../apps/pwa/src/pages/SettingsPage.tsx)).

## Endpoint coverage

258 server route paths: 110 reached by native, 89 by the PWA, 71 by both, 130 by neither (admin, manager,
fleet and federation routes, plus dead ones). Full lists in
[`docs/parity/endpoint-matrix.md`](parity/endpoint-matrix.md).

The native-only set is dominated by two clusters that simply do not exist on the web: **Pulse/channels**
(14 routes) and **two-layer recovery** — `recovery/collect/*`, `recovery/shares/*`, `recovery/pin/*`,
`approve-keeper` (17 routes), plus `push-tokens`, `messages/react`, `messages/edit`, `trust/profile`.
The PWA-only set is mostly device pairing (`pair/init`, `pair/poll`, `pair/cancel` — the PWA is the QR
*display* side, native the scanner), commons/vote and the legacy `recovery/approve`/`reject`.

**Caveat on that matrix:** a path built from a variable segment (native's `/api/recovery/${decision}`) is
matched by pattern, so a client can look like it misses a route it actually reaches. Method mismatches are
checked for the PWA only — finding 3 above was found by hand, and a native-side method-aware sweep is still
outstanding.

## Second pass: the remaining leads, now checked

A follow-up verification run ([`docs/parity/verification.md`](parity/verification.md)) confirmed, refuted or
qualified all eight leads from the first pass.

**Refuted — recovery is not stranded.** Both clients derive the same keypair from the same 12 words
([native crypto.ts:158-174](../apps/native/utils/crypto.ts), [PWA mnemonic.ts:56-97](../apps/pwa/src/lib/mnemonic.ts)),
so an account created on either platform restores on the other by seed phrase. Only the *secondary* flows
diverge — PWA does legacy guardian requests, native does keeper/SSO — which is finding 2 above, not an
account-loss trap. The first pass overstated this as "cannot be recovered from the other".

**Confirmed.** The PWA reconnects its WebSocket on a flat 5s interval with no keep-alive, against native's
exponential backoff with jitter and 30s pings. The PWA's "−20 with a small welcome voucher" Newcomer floor is
simply wrong — no −20 allowance exists anywhere in server execution logic, and native's 0 is correct. The
3-month inactivity suspension warning in `BalanceInfoModal` is fiction; nothing enforces it. Native's
group-conversation code path has no caller that passes `'group'`.

**Qualified.** Pairing is genuinely one-directional (PWA displays the QR, native scans it), but migration is
not impossible — the seed phrase covers every direction. On key storage, the unencrypted IndexedDB persistence
and the total absence of a passcode or biometric gate on the web are confirmed, though one cited detail about
`localforage` was wrong. The guardian "2 of 3 majority" copy does contradict `RECOVERY_THRESHOLD = 3`, with a
caveat on the modal's own existence claim.

The floor, guardian-threshold and suspension items overlap the existing app-copy-vs-code audit, so they are
known and still unfixed.

## Suggested order

1. Findings 1 and 2 — they cost people their accounts, and 1 is a one-line fix.
2. Finding 3 — native voting is broken outright.
3. Findings 4 and 5 — wrong numbers and wrong rules, shown to everyone, cheap to correct.
4. Findings 6, 7, 8 — decide per item whether to build it on the web or stop advertising it.
5. Finding 9 — a scoping decision, not a bug: is the PWA meant to reach Pulse parity, or be the light client?
6. Fix [README.md:433](../README.md) either way, so the claim matches whichever answer you pick.
